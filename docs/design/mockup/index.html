Step 5 is the entire ML integration. forecast is a member of the same operation union as summarize and join — so it inherits the permission filter at step 4, renders in a stock chart, and caches under the existing query_results key. It is the one deliberate pipeline break: ibis cannot express Holt-Winters, so the operation materialises the upstream frame under the row cap and hands it to statsmodels.
Realised SQL — dry run
-- not executed yet · 4 operations compiled -- step 5 (forecast) runs on the returned frame SELECT date_trunc('month', pe.posting_date) AS period, SUM(pe.paid_amount) AS collected FROM "tabPayment Entry" pe JOIN "tabCustomer" c ON c.name = pe.party WHERE pe.docstatus = 1 AND c.territory IN (…4 permitted) GROUP BY 1 ORDER BY 1 LIMIT 10000
The dry-run compiles and shows the SQL without executing it. The forecast never sees a row your permissions removed, because the filter is injected upstream of the materialisation — not applied to the model's output.
